# Agent 心智模型的演进

我们从“调用一次模型 API”出发，逐步搭建一个能使用工具、接收行动结果、控制执行权限的 Agent。下面沿着具体任务，说明每一节遇到了什么问题、新机制如何解决它，以及我们对 Agent 的理解因此发生了什么变化。

| 阶段 | 心智模型 | 新增的认识 |
|---|---|---|
| 起点 | 输入 → 模型 → 回答 | 一次模型请求产生一次响应 |
| S01 | 模型 → 工具 → 结果 → 模型 | 把行动结果交回模型，才能继续行动 |
| S02 | 循环 + 工具声明 + 字典分发 | 用统一的调用方式连接不同能力 |
| S03 | 循环 + 工具分发 + 权限判断 | 模型提出行动，程序决定是否允许执行 |
| S04 | 循环 + 固定时机 + 回调注册 | 把权限、日志等扩展挂到循环的对应位置 |
| S05 | 循环 + 显式任务清单 + 进度提醒 | 把整体计划和当前进度变成可持续更新的状态 |
| S06 | 主循环 + 独立上下文的子循环 | 把局部任务交出去，只将最终结论带回主对话 |
| S07 | 技能目录 + 按需加载操作指南 | 先让模型知道有哪些知识，再把当前需要的说明加入对话 |
| S08 | 有限上下文 + 原始记录留档 + 分层压缩 | 控制每次交给模型的信息量，保留继续任务所需的状态 |
| S09 | 持久记忆 + 相关性选择 + 回合后提取 | 把以后仍有用的知识留下来，在新任务中按需取回 |
| S10 | 持久任务图 + 认领 + 依赖解锁 | 让程序根据已保存的任务状态判断下一项工作能否开始 |
| S11 | 后台执行 + 启动确认 + 延迟结果通知 | 把发起行动和收到最终结果分开，让独立工作可以交错进行 |
| S12 | 时间匹配 + 到期队列 + 空闲时启动回合 | 让时间成为任务的入口，到点后主动把工作交给 Agent |
| S13 | 持久队友 + 独立上下文 + 消息协作 + 共享任务板 | 让多个行动循环并行工作，并由运行时协调任务归属与结果交付 |
| S14 | 外部工具发现 + 动态工具池 + 宿主权限策略 | 工具可以来自外部服务，发现后仍接入同一个行动反馈循环 |
| S15 | 统一循环 + 上下文准备 + 受控执行 + 事件回流 | 把各节机制接入同一个运行时，明确状态如何进入模型、执行结果如何回来 |
| S16 | 已保存的流程 + 并行编排 + 结果校验 + 日志恢复 | 把重复的步骤顺序写进代码，让模型处理各步内容，已完成的调用可从日志复用 |
| S17 | 完成条件 + 独立判断 + 未完成时继续循环 | 把模型想结束当前回合与用户目标是否完成分开判断 |

## S01：从一次问答到行动反馈循环

代码：[s01_agent_loop.py](s01_agent_loop.py)

**原来的理解：** 调用模型，拿到回答，程序结束。

例如用户要求：“读取 a.txt，并概括里面的内容。”模型无法仅凭这句话知道本机文件里写了什么，需要通过工具取得内容。

我们给模型提供一个 Bash 工具。模型可以返回“执行 `cat a.txt`”的工具调用请求，由 Python 程序执行命令，再把读到的内容交回模型。模型看到文件内容后，才能生成概括；如果还需要别的信息，也可以继续请求工具。

原本需要人手动“执行命令、复制结果、再问模型”的过程，就这样变成了程序里的循环：

```text
用户输入 → 模型响应
              ├─ 没有工具调用 → 输出回答
              └─ 有工具调用 → 执行 Bash → 追加结果 → 再次请求模型
```

每轮都把行动请求和执行结果加入历史，并将这份历史作为下一次模型请求的输入。这样模型才能知道用户要做什么、之前执行过什么、执行结果是什么。

工具调用本身只是一条请求，实际操作由程序完成。程序执行完也不代表整个任务结束，还要把结果交回模型，继续生成回答或提出下一次行动。

**升级后的理解：Agent 的最小运行机制，是模型决策与真实执行之间不断往返的循环。**

## S02：从一个 Bash 工具到一组可分发的能力

代码：[s02_tool_use.py](s02_tool_use.py)

**上一节的局限：** 所有行动都经过 Bash，读写文件也需要模型先拼接 Shell 命令。

Bash 已经可以完成许多操作，但模型需要把“读取文件”翻译成 Shell 命令。随着任务增加，每种操作都要通过拼命令来表达。

这一节增加文件读取、写入、编辑和查找工具。仍然以读取 a.txt 为例，模型现在可以直接请求读取工具，并传入文件路径，不必先生成 `cat` 命令。

工具多了以后，程序需要根据模型返回的工具名，找到对应的实现函数。这就是“工具分发”：

```text
模型返回工具名和参数
        ↓
按工具名分发到对应函数
        ↓
把执行结果交回模型
```

工具有两个面向不同对象的部分：

- 工具声明：交给模型，描述工具的名称、用途和参数，让模型知道有哪些能力、如何请求使用。
- 工具实现与分发：留在程序里，用“工具名 → 函数”的对应关系，找到并执行实际操作。

例如模型请求读取文件，程序找到读取函数，执行后回传文件内容。这里实际执行的仍是我们写的 Python 函数；模型负责选择工具和提供参数。

从一个工具变成多个工具，改变的是可用的行动和查找处理函数的方式。“请求模型 → 执行工具 → 回传结果”的循环不需要为每种工具重新设计。

**升级后的理解：循环负责推进任务，工具集合提供行动能力，分发表把模型的请求连接到具体函数。** 增加工具主要修改声明和处理函数，不必为每种工具重写循环。

## S03：从工具请求到经过授权的行动

代码：[s03_permission.py](s03_permission.py)

**上一节的局限：** 我们已经解决了“模型能使用哪些工具、如何执行”的问题，但还没有统一回答“这一次调用是否允许执行”。

例如用户要求“清理临时文件”，模型可能提出删除命令。程序知道如何执行这条命令，却仍需要先判断：它是否被禁止？是否需要用户确认？判断应该发生在操作真正执行之前。

这一节在工具执行前加入权限判断。硬拒绝规则表示始终禁止；其他规则找出需要用户审批的操作；未命中规则的调用直接放行：

```text
模型提出工具调用
        ↓
硬拒绝列表 ── 命中 → 拒绝
        ↓ 未命中
规则匹配 ──── 未命中 → 执行工具
        ↓ 命中
用户审批 ──── 同意 → 执行工具
        └──── 拒绝 → 不执行

执行结果或拒绝结果 → 交回模型 → 下一轮
```

如果用户同意删除，程序才执行工具，再把执行结果交回模型。如果用户拒绝，程序跳过实际操作，把“权限被拒绝”作为工具结果交回。

拒绝也属于反馈：模型需要知道行动没有发生，才能换一种做法或向用户解释。权限判断由此接入了 S01 的循环，而不是在循环外留下一个模型不知道的决定。

**升级后的理解：模型负责提出行动，权限管线负责决定能否执行，工具负责实际执行；成功、失败和拒绝都进入反馈循环。**

## S04：从循环中的具体检查到固定的扩展位置

代码：[s04_hooks.py](s04_hooks.py)

**上一节的局限：** 权限判断已经有了，但循环直接调用权限检查。接下来如果要在执行前记录日志、执行后检查输出、结束时统计调用次数，每增加一种行为，就要继续修改循环。

例如同样是读取 a.txt，我们现在希望“先检查权限，再记录本次调用，读取后检查输出大小”。这些行为发生的时机很明确，却承担着不同职责。把它们都写进循环，会让循环越来越难看清。

这一节引入 Hook：把一个普通函数注册到某个固定时机，运行到那里时调用它。循环知道何时触发，注册的函数负责具体做什么。

| 时机 | 发生什么 | 可以挂接的行为 |
|---|---|---|
| 用户提交输入 | 即将把任务交给模型 | 记录输入、准备上下文 |
| 工具执行前 | 已拿到工具请求，尚未执行 | 权限判断、调用日志 |
| 工具执行后 | 已拿到执行结果 | 输出检查、执行后处理 |
| 模型准备结束 | 本轮没有新的工具调用 | 统计收尾，或补充要求让模型继续 |

```text
用户输入 → 输入 Hook → 请求模型
                          ├─ 工具调用 → 执行前 Hook
                          │                 ├─ 拦截 → 拒绝结果
                          │                 └─ 放行 → 工具 → 执行后 Hook → 结果
                          │                              ↓
                          │                    结果加入历史，再次请求模型
                          └─ 准备结束 → 结束 Hook
                                           ├─ 允许结束 → 返回回答
                                           └─ 补充要求 → 加入历史，再次请求模型
```

S03 的权限判断仍然存在，只是现在注册成执行前的 Hook。需要增加日志时，再注册一个同一时机的函数；循环里的调用位置不需要跟着增加。执行前的 Hook 一旦返回拦截原因，后续前置 Hook 和工具就会跳过，这个原因作为工具结果交回模型。

结束 Hook 则让我们看到另一种控制：模型给出回答后，程序也可以补充“再检查一次结果”的要求，将其作为新消息送回模型。模型暂时没有工具调用，不一定意味着程序必须立即结束。

**升级后的理解：循环提供稳定的执行时机，Hook 承接这些时机上的具体策略。** 工具决定有哪些行动能力，Hook 决定在行动和结束前后附加哪些行为。

## S05：从连续行动到显式维护计划和进度

代码：[s05_todo_write.py](s05_todo_write.py)

**上一节的局限：** 我们已经可以在执行前后挂接扩展，但任务的整体安排仍然散落在对话里。模型能根据最近的工具结果继续行动，却可能在处理局部问题时漏掉原来的其他要求。

例如用户要求“给两个脚本补上类型注解，再运行测试”。模型修改第一个脚本后发现一个错误，接着花了多轮排查；即使修好了错误，仍需要记得第二个脚本和最后的测试。

这一节加入 `todo_write`，让模型把计划写成一份明确的任务清单，并在执行过程中更新状态。例如：

```text
[x] 检查两个脚本
[>] 补充类型注解
[ ] 运行测试
```

清单由程序保存在内存中，每次更新都把当前清单返回给模型，也显示给用户。这样“还有什么没做”和“现在做到哪里”就有了明确的表达。更新时提交的是当前完整清单。

模型仍通过已有工具完成实际工作。`todo_write` 改变的是计划状态，读取文件、修改代码和运行测试仍由各自的工具负责。一次任务期望形成这样的过程：

```text
用户提出多步任务
        ↓
模型列出计划 → todo_write 保存并回显清单
        ↓
模型选择一步 → 执行普通工具 → 取得结果
        ↓
模型更新待办状态 → 选择下一步，或给出最终回答
```

只有清单还不够：模型也可能一直调用其他工具而不更新进度。因此程序在连续三个工具调用轮次未使用 `todo_write` 后，把“更新待办清单”的提醒加入下一次模型输入。一轮可以包含多个工具调用，提醒关注的是连续行动了几轮。

这里的职责仍然清楚：模型负责拟定和更新计划，程序负责保存状态、检查清单的基本约束并适时提醒。状态由模型更新，普通工具执行完不会自动勾选任务；清单中的“完成”也不能代替实际结果验证。

**升级后的理解：Agent 除了需要行动反馈，也可以借助显式任务状态维持对整体目标的关注。** 这是对计划和进度的辅助，不会替模型自动安排执行顺序或保证任务完成。

## S06：从一个对话处理所有细节到委派独立子任务

代码：[s06_subagent.py](s06_subagent.py)

**上一节的局限：** 待办清单能帮助模型记住整体安排，但所有工作仍然在同一段对话中进行。为了完成一个局部调查，模型可能读取很多文件、尝试多次命令，这些过程都会留在主对话里。

例如用户要求“修复登录失败，并补充测试”。主 Agent 可以先把“查清登录请求经过哪些函数、错误在哪里产生”交给子 Agent。子 Agent 自己查找文件、阅读代码，最后返回调用链和相关位置；主 Agent 根据这些结论继续修改和验证。

这一节加入 `task` 工具。它的内部仍然是我们已经熟悉的“模型 → 工具 → 结果 → 模型”循环，只是使用一份新的对话历史：

```text
主 Agent：用户目标、已有讨论、整体决策
        ↓ task("查清登录调用链，返回相关文件和函数")
子 Agent：子任务说明 → 读取文件 → 分析 → 最终结论
        ↓ 只将最终文本作为 task 的结果返回
主 Agent：结合结论继续修改、测试
```

子 Agent 看不到主对话，所以委派时要交代清楚目标、必要背景和希望得到的结果。它的内部工具调用和输出不会逐条加入主对话，但最终结论会作为普通工具结果交回，供主 Agent 继续使用。

这里隔离的是对话上下文。父子仍然共享工作目录：子 Agent 修改的文件，主 Agent 也能读到；工具也经过相同的权限和 Hook。它不是另一个独立沙箱。

本节按教程只给子 Agent 基础工具，不提供 `task`，因此只能委派一层。主 Agent 会等待子任务结束后再继续，这是顺序执行。为聚焦这个机制，本节使用基础工具和 Hook，没有叠加 S05 的待办清单。

子 Agent 返回的仍是模型生成的结论，与待办清单中的“完成”一样，不能直接当作验证证据。主 Agent 需要结合相关文件、命令结果和测试判断任务是否完成。

**升级后的理解：一个 Agent 可以把另一个 Agent 循环当作工具，用独立上下文完成局部工作，再把结论接回自己的行动反馈循环。**

## S07：从把所有规范塞进提示词到按需加载技能

代码：[s07_skill_loading.py](s07_skill_loading.py)

**新的问题：** 我们已经能调用工具，也能委派子任务，但“应该怎样完成某类任务”的经验还没有专门的存放方式。例如代码审查有审查步骤，数据库开发有 SQL 规范。如果把这些说明全部写入系统提示词，每次请求都会携带大量与当前任务无关的内容。

这一节把操作指南放进 `experiments/skills/*/SKILL.md`。每份文件开头用 YAML 写技能名称和适用场景，正文再写详细步骤。启动时，程序扫描这些文件，只把名称和描述组成目录放进系统提示词；模型判断某个技能适用时，再通过 `load_skill` 取得完整内容。

例如用户要求审查代码，可以形成这样的过程：

```text
启动：读取技能文件 → 系统提示词中只放名称和描述
        ↓
用户：“审查这段代码”
        ↓
模型看到 code-review 的适用描述 → 调用 load_skill("code-review")
        ↓
完整 SKILL.md 作为工具结果加入对话
        ↓
模型参考审查步骤 → 读取代码、检查调用 → 给出发现
```

这里的“按需”指的是何时把全文交给模型：本节实现会在启动时读取并缓存文件，但不会立即把所有正文发送给模型。加载后的内容进入普通对话历史，之后的请求也会携带它。

Skill 提供的是做事方法，实际读取文件、运行命令仍然依靠工具；它也不会启动 S06 那样的独立子循环。可以分别理解为：工具提供行动能力，子 Agent 承接局部工作，Skill 提供完成某类工作的指导。加载指导后是否正确执行，仍需要结合实际结果判断。

本节按教程保留基础工具和 Hook，聚焦技能加载。仓库提供了一个 [code-review 示例](skills/code-review/SKILL.md)，在项目根目录运行后，可以输入“加载 code-review 技能，审查 experiments/s01_agent_loop.py”来观察这个过程。

**升级后的理解：Agent 不必一开始就携带全部操作知识，可以先知道有哪些指南，再将当前任务需要的内容接入行动反馈循环。**

## S08：从不断追加历史到主动管理有限上下文

代码：[s08_context_compact.py](s08_context_compact.py)

**上一节之后仍然存在的问题：** Skill 让我们不用一开始就加载所有指南，但 Agent 在执行过程中仍会不断积累消息。读过的文件、测试日志和分析都会留在历史里，并随着下一次请求重新交给模型。工作足够久，上下文最终还是会满。

例如用户要求“排查登录失败并补充测试”。Agent 先后读取多个文件，又运行了多次测试。到准备修改代码时，历史中可能已有大量旧日志，而当前真正需要的是：问题原因、修改决定、用户约束，以及还没完成的验证。

这一节在每次请求模型前加入压缩管线。先处理能够从磁盘恢复的细节，空间仍然不够时再生成摘要：

| 顺序 | 处理什么 | 上下文中留下什么 |
|---|---|---|
| 大结果转存 | 最新一批工具结果超过预算 | 文件路径和内容预览 |
| 旧消息归档 | 消息条数过多 | 开头、最近消息和完整记录的路径 |
| 旧结果缩减 | 上下文仍然过大 | 较早结果的恢复路径，保留最近结果 |
| 历史摘要 | 上述处理后仍然过大 | 当前用户请求、任务状态摘要和完整记录路径 |

前三步不需要调用模型。如果最新工具结果本身就很大，也可以先落盘、保留预览，让模型先看到主要内容。最后的历史摘要才会增加一次模型调用，整理目标、决定、相关文件、剩余工作和用户约束。

```text
用户请求 → 模型 → 工具 → 追加结果
              ↑             ↓
              └─ 压缩管线 ← 检查历史
                   ├─ 转存、归档、缩减已够用 → 继续请求模型
                   └─ 仍然过大 → 保存原始记录 → 生成摘要 → 继续请求模型
```

这里有两种不同的信息：**当前用户请求说明现在要做什么，历史摘要说明之前发生了什么。** 压缩后仍保留系统指令，并将当前请求与摘要明确分开，避免把历史里的一段工具输出当成新的用户要求。摘要可能遗漏细节，所以工具原始结果保存在 `.task_outputs/tool-results/`，历史记录保存在 `.transcripts/`，需要时可以重新读取。

模型也能调用 `compact` 主动请求压缩。程序会先执行完同一批次的所有工具，并记录每个结果，再总结这一轮，避免已经完成的文件操作在摘要中丢失。归档时也要让工具调用和对应结果一起保留，保证下一次请求的消息结构完整。

本节沿用教程，用字符数估算上下文大小，并不等同于模型实际计算的 token 数。如果 API 仍然明确报告上下文超限，程序会保留近期消息、总结更早历史，再重试一次；再次失败则暴露错误。

本节保留基础工具和 Hook，聚焦压缩机制。在项目根目录运行后，可以输入“读取 experiments/NOTE.md，然后调用 compact，最后说明当前任务和下一步”，观察摘要调用与留档文件。磁盘留档不会自动成为下一次会话的记忆；跨会话保存和检索信息是后续课程的内容。

**升级后的理解：Agent 不仅要决定下一步做什么，还要管理下一步能看到什么。历史可以留在磁盘上，模型上下文则需要保留当前任务所需的信息，并允许按需找回细节。**

## S09：从保存会话记录到积累跨会话知识

代码：[s09_memory.py](s09_memory.py)

**上一节的局限：** 压缩让一个长任务可以继续进行，但重新启动程序后，新的对话历史仍然是空的。即使原始记录还在磁盘上，程序也不会自动知道哪条旧信息对新任务有用。

例如用户说“以后这个项目统一用 uv 管理依赖”。这次任务完成后，新会话中用户只说“加一个依赖”，我们希望 Agent 能取回这条约定，而不是每次都要求用户重复说明。相反，“这次先不要运行测试”只约束当前任务，不应该变成永久规则。

这一节在工作目录的 `.memory/` 中保存独立的记忆文件，并用 `MEMORY.md` 记录名称和简短描述。它保留四类知识：用户偏好、长期反馈、项目事实和外部参考线索。记录可以来自本轮对话，但不是把整段对话换个名字保存下来。

```text
第一次会话
用户：“以后统一用 uv 管理依赖” → Agent 完成任务
        ↓
模型提取候选 → 程序检查持久性和重复内容 → 写入 .memory/ 并更新索引

新会话
用户：“加一个依赖” → 根据请求和记忆目录选择相关记录
        ↓
加载所选正文 → 作为背景知识交给模型 → 使用 uv 完成任务
```

这形成了四个环节：

| 环节 | 负责什么 |
|---|---|
| 存储 | 每条知识单独落盘，并维护可浏览的索引 |
| 召回 | 根据最近的用户请求选择相关记录，再加载正文，限制总长度 |
| 提取 | 回合结束后，从对话中找出以后仍可能有用的候选信息 |
| 整理 | 记录达到数量阈值后，合并重复内容、更新过期知识 |

模型返回的候选不能直接当作可靠事实。程序检查字段和记忆类型，区分 `persistent` 与 `current_task`，过滤带临时含义或与已有内容重复的候选。提取输入也排除了系统提示词和工具输出，减少把召回内容或执行日志再次当成新知识的机会。这些规则只能辅助筛选，记忆内容本身仍然可能有误，需要结合实际情况判断。

召回内容作为背景知识加入系统提示词，并明确要求：**如果旧记忆与当前用户请求冲突，以当前请求为准。** 记忆能够影响模型如何做事，但不会成为新的用户命令。

记录积累到十条时，本节会调用模型生成整理后的列表。新列表先整体校验，写入和删除过程中出错则恢复旧记录，再暴露错误。与教程中的降级分支相比，本实验让模型调用、解析和文件错误直接暴露，方便学习时定位问题。

与 S08 相比，压缩管理的是“当前任务接下来还能看到多少历史”，记忆管理的是“下次任务还值得知道什么”。本节按教程独立演示记忆，保留基础工具和 Hook，没有叠加压缩管线。召回选择、回合后的提取，以及达到阈值后的整理，都会按需增加模型调用。

可以在项目根目录运行后输入“请记住：以后这个项目用 uv 管理依赖”，检查 `.memory/`；退出并重新启动，再问“这个项目用什么管理依赖”，观察新会话能否召回。最终以记忆文件的实际内容和新会话的回答判断效果。

**升级后的理解：Agent 的对话上下文会结束，但选择性保存的知识可以留在外部存储中，并在新的行动反馈循环里重新发挥作用。**

## S10：从记录待办事项到维护可恢复的任务图

代码：[s10_task_system.py](s10_task_system.py)

**前面机制的局限：** S05 的清单可以显示“接下来做什么”，但保存在进程内，退出后就丢失了，也没有表达任务之间的先后约束。S09 保存的是以后仍有用的知识，当前工作完成到哪一步，则需要专门的任务状态。

例如开发一个接口，要先确定数据库表，再编写接口，最后运行接口测试。同时，数据库表确定后就可以开始写文档。这些工作形成了依赖关系：

```text
确定数据库表 → 编写接口 → 运行接口测试
      └────→ 编写文档
```

这一节给每个任务分配独立 ID，将描述、状态、负责人和前置任务写入工作目录的 `.tasks/`。其中 `blockedBy` 保存前置任务的 ID。程序在认领任务前读取这些记录，只有前置任务全部标记完成，才允许开始。

任务图分两步建立：先调用 `create_task` 创建各个节点，拿到程序返回的 ID；再调用 `update_task`，使用这些实际 ID 添加依赖。模型在一轮中提出多个创建请求时，还没有看到工具结果，因此不能预先知道其他新任务的 ID。

建立依赖时，程序会拒绝不存在的任务、自依赖和循环依赖，并在整次修改检查通过后才保存。重复添加相同依赖不会产生重复关系。

每个任务通过两个动作推进：

```text
pending ── claim_task ──→ in_progress ── complete_task ──→ completed
             ↓                              ↓
       检查前置任务并记录负责人         检查当前状态和负责人
                                            ↓
                                报告刚刚解除阻塞的下游任务
```

例如“确定数据库表”完成后，“编写接口”和“编写文档”具备了开始条件，但状态仍然是 `pending`。模型需要选择并认领下一项任务，程序不会自动替它执行工作。本节按教程顺序执行，负责人字段用于记录任务归属。

与 S05 相比，现在程序能够约束依赖和状态转换，并把进度留在磁盘上；**完成状态仍由模型调用 `complete_task` 写入，实际修改和测试结果仍需核实。** 依赖解锁表示前置任务的状态满足条件，不能代替对工作结果的验证。

重启后，Agent 可以通过 `list_tasks` 找回任务，通过 `get_task` 读取完整说明，再结合文件和执行结果继续工作。这样保存下来的不只是一份任务名称列表，还包含任务之间的关系以及当前进展。

本节独立演示任务系统，保留基础工具和 Hook。可以输入“创建检查代码、修改代码、运行测试三个任务，按顺序建立依赖，先只列出任务”，观察 `.tasks/` 中的记录；重启后再要求列举任务并查看某一项的完整说明。

**升级后的理解：计划可以成为程序能够读取和约束的持久状态。模型负责选择并执行工作，任务系统负责记录进度、检查依赖，并让这些信息在新会话中继续可用。**

## S11：从等待工具返回到在后台执行慢操作

代码：[s11_background_tasks.py](s11_background_tasks.py)

**上一节之后仍有的限制：** 任务图能表达哪些工作可以开始，但执行一个耗时命令时，主循环仍然要等待。例如测试运行需要两分钟，在它结束之前，同一轮中的文件读取和下一次模型请求都会停下来。

如果接下来要做的事不依赖测试结果，这段等待可以用来继续工作。例如启动测试后先阅读说明文档，等结果回来，再决定是否需要修复代码。

这一节给 `bash` 增加 `run_in_background` 参数。模型明确传入 `true` 时，程序先在主线程完成权限检查，再将命令交给后台线程，立即返回一个 `bg_0001` 这样的任务 ID。其他工具和普通 Bash 调用仍按同步方式执行。

```text
模型请求：后台运行测试
        ↓
权限检查 → 后台线程启动命令
        ↓              │
工具返回启动确认和 ID   │ 测试持续运行
        ↓              │
主循环继续读取文档      │
        ↓              ↓
下一轮开始 ← 收集已完成的结果
        ↓
将任务状态和结果摘要作为通知加入对话 → 模型结合结果继续工作
```

这里最重要的区别是：**“命令已启动”与“命令已完成”是两个不同的反馈。** 原始工具调用只收到一次启动确认；后来的结果以独立的 `<task_notification>` 消息加入对话，包含后台 ID、成功或失败状态、命令及输出摘要。程序由此明确区分两类反馈，模型仍需根据最终结果判断工作是否成功。

对应地，后台路径的执行后 Hook 收到的是启动确认。命令的退出码、超时或线程中的异常，要到结果通知里才能看到。非零退出和执行异常都会标记为失败；程序还负责命令超时和退出时的进程清理。

完成通知只在每次请求模型前收集。**后台命令完成不会自动唤醒 Agent。** 如果主循环已经返回并等待用户输入，通知会在下次用户发起请求时加入对话。本节没有为了等待结果而持续调用模型。

后台执行适合彼此独立的工作。需要使用命令结果的后续步骤，仍然要等结果回来；模型负责判断是否存在这种依赖。S10 的任务 ID 标识持久的工作事项，S11 的后台 ID 标识当前进程中的一条运行命令，两者承担不同职责。

本节按教程以基础工具和 Hook 演示后台机制，运行状态保存在内存中。可以输入“后台执行一条两秒后输出 done 的 Python 命令，同时查找 experiments 下的 Python 文件”；如果主循环提前结束，等两秒后再输入“检查后台结果”，观察启动确认与完成通知出现的时机。

**升级后的理解：Agent 的行动反馈可以延迟到达。主循环先取得行动已启动的确认，继续处理独立工作，再在后续轮次接收完成事件并作出判断。**

## S12：从用户发起工作到时间触发工作

代码：[s12_cron_scheduler.py](s12_cron_scheduler.py)

**上一节之后仍有的限制：** S11 可以让已经启动的命令在后台执行，但“每天早上九点跑测试”还需要人到点后发送请求。Agent 需要记住将来的安排，并在时间到达时主动开始一轮工作。

这一节增加 `schedule_cron`、`list_crons` 和 `cancel_cron`。例如注册“每天九点检查测试”，保存的是执行时间和提示词；到点后，程序把提示词交给模型，模型再按普通工具循环选择命令、取得结果并回答。

```text
注册：0 9 * * * → 检查测试
        ↓
调度线程检查本地时间 → 到期后进入队列
                              ↓
                    队列处理线程等待 Agent 空闲
                              ↓
                    追加 [Scheduled] 检查测试
                              ↓
                    模型 → 工具 → 结果 → 模型
```

两个线程分工不同：调度线程只判断什么时候到期，队列处理线程负责启动 Agent。用户正在进行的回合与定时回合共用一把锁，避免同时修改同一份对话。**即使终端正在等待用户输入，队列处理线程也可以启动定时回合。** 这与 S11 只在下一次请求模型前收集完成通知不同。

本节沿用教程的五段式 Cron，顺序是“分钟、小时、日、月、星期”，按进程的本地时间匹配，精度为分钟。例如：

| 表达式 | 含义 |
|---|---|
| `* * * * *` | 每分钟 |
| `*/5 * * * *` | 每五分钟 |
| `0 9 * * *` | 每天九点 |
| `0 9 * * 1-5` | 工作日九点 |

任务可以是周期任务，也可以设置 `recurring=false`，在下一次匹配时交付一次。默认 `durable=true`，定义和待交付状态保存在工作目录的 `.scheduled_tasks.json`；设为 `false` 则仅保存在本次进程中。

到期入队和模型接收之间可能相隔一段时间，因此程序分别记录“正在等待交付”和“当前分钟已经触发”。这样 Agent 忙碌时，调度线程不会每秒重复加入同一项工作。模型请求失败时，待交付提示词从对话中撤回，并恢复到队列；错误会明确暴露，不会伪装成功。

模型成功返回有效响应后，程序确认交付：一次性任务删除，周期任务等待下一次匹配。**这只说明提示词已经交给模型，不说明测试已经运行或工作已经完成。** 如果此后工具执行失败，仍要根据工具结果判断。交付采用“至少一次”的语义：若模型已经接收，而程序尚未保存确认就退出，重启后可能重复交付。

持久化也不意味着程序关闭后仍会执行。进程必须保持运行才会检查时间；重启只恢复定义和此前已到期的待交付任务，不补跑停机期间错过的时间点。定时回合在后台线程运行，需要交互审批的工具调用会直接拒绝，以免与终端输入冲突。

本节独立演示调度机制，保留基础工具和 Hook。可以输入“每分钟执行一次 date，仅本次会话有效”，随后保持进程运行，观察不再输入消息时是否仍会启动回合，再要求列举和取消任务。

**升级后的理解：行动反馈循环可以由外部事件启动。用户输入是一种入口，时间到期也是一种入口；调度器负责何时交付工作，Agent 循环负责收到工作之后如何执行。**

## S13：从一次性委派到持续协作的团队

代码：[s13_agent_teams.py](s13_agent_teams.py)

**前面机制的局限：** S06 已经能把局部任务交给独立上下文的子 Agent，但主循环要等待它返回，子 Agent 返回结论后就结束。面对“分别检查配置加载与认证模块，再一起判断问题”这样的工作，我们希望两边能同时调查，完成后还能接着合作。

这一节引入 Lead 和持久队友。Lead 负责用户对话、分工与汇总；每个队友在线程中运行自己的模型与工具循环，保存独立的对话历史。队友完成一项工作后进入 IDLE，收到新消息或认领到下一项任务，再回到 WORK。

```text
用户目标 → Lead 创建任务、安排分工
               ├─ 队友 alice：独立上下文 → 工具循环 → 结果
               └─ 队友 bob：  独立上下文 → 工具循环 → 结果
                                                     ↓
                                      收件箱事件 → 唤醒 Lead → 汇总或继续协调

队友生命周期：WORK → IDLE → 新消息 / 新任务 → WORK → … → 关机
```

例如 alice 调查配置模块，bob 调查认证模块。两边读取的文件和工具结果留在各自的历史中；Lead 收到的是它们发来的消息和结论。这样既能同时推进独立工作，也避免把所有调查细节塞进 Lead 的上下文。与 S06 的一次性子调用相比，队友的身份和上下文可以跨多项任务保留，但本节没有把完整会话保存到磁盘，重启不会恢复这些线程和对话。

教程要求 Lead 先提出小规模分工，用户确认后才调用 `spawn_teammate`。目前这条要求写在系统提示词中，由模型遵守。分工应写清负责的文件和职责；队友共享仓库时，独立上下文不会自动避免文件修改冲突。

### 消息由运行时交付

Agent 之间通过 `.mailboxes/` 下的文件收件箱通信。模型可以使用 `send_message` 协调工作，运行时负责读收件箱，把消息追加到对应 Agent 的上下文。Lead 没有 `check_inbox` 工具，也不需要反复调用工具等待队友：终端等待输入时，运行时同时检查团队事件，收到事件就启动下一轮 Lead 调用。

队友结束工作回合时，运行时分别发送两种事件：

| 事件 | 回答的问题 |
|---|---|
| `result` | 这次工作得出了什么结论？ |
| `idle_notification` | 这个队友现在是否进入等待状态？ |

结果文本、队友是否空闲、任务板是否标记完成，是不同的信息。队友需要调用 `complete_task` 更新任务状态；运行时不会因为它说“完成了”就自动完成任务。**任务状态仍不能代替文件改动和测试结果的验证。**

### 共享任务板协调工作归属

本节沿用 S10 的任务和依赖：先创建节点，取得真实 ID，再添加依赖。Lead 可以修改任务图，队友只能查看、认领和完成任务。每个队友同时只持有一项任务，没有认领任务时不能使用工作区工具。

空闲队友先处理收件箱里的指令；没有消息时，再从共享任务板寻找无人认领、依赖已完成的任务。找到候选不代表已经拥有它，真正的认领必须在锁内再次检查并保存所有者。两个队友同时发现同一项任务时，只允许一个认领成功。

例如“检查配置”和“检查认证”完成后，“汇总兼容性问题”解除阻塞。空闲队友可以直接认领它，继续使用原来的上下文和工具循环，而不必让 Lead 再逐条派发。

### 工作目录和控制协议

需要隔开并行修改时，Lead 可以在认领前创建任务绑定的 Git worktree。队友的文件与 Shell 工具随后使用该任务的目录；未绑定的任务使用原仓库目录。任务完成后，目录绑定保留到当前工作回合结束，避免同一轮后续工具突然切换目录。Worktree 分开目录和分支，不提供安全沙箱，也不会自动合并成果；检查、合并和清理由用户或宿主处理。

关机和计划审批则使用带类型与请求 ID 的控制消息。例如 Lead 要求队友先交计划，队友提交后进入等待，Lead 再批准或要求修改。**计划审批由程序约束执行：未获批准时，文件读取可以继续，Bash、写入和编辑会被阻止。** 审批还关联当前任务，旧任务的批准不能用于新的工作。队友需要交互审批的危险调用会被拒绝，不会从后台线程读取终端。

本节独立组合基础工具、Hook、任务系统和团队机制，没有叠加 S11 后台命令或 S12 定时调度。实现沿用教程的 Unix 文件锁和终端事件等待方式。可以先输入“建议两名队友，分别检查 experiments/s01_agent_loop.py 和 experiments/s02_tool_use.py，只读检查，完成后汇总并关闭队友”；确认分工后，观察任务认领、结果事件、Lead 自动唤醒及关机确认。

**升级后的理解：团队由多个独立的行动反馈循环组成。模型负责各自的工作和协作决策，运行时负责消息交付、任务所有权、工作目录和控制协议，让这些循环能够持续协作。**

## S14：从手写工具集合到发现外部服务的能力

代码：[s14_mcp_plugin.py](s14_mcp_plugin.py)

**前面机制的局限：** 多个 Agent 可以协作，但它们可用的工具仍由我们预先写在程序里。假设要接入文档搜索和部署平台，每个服务都需要单独维护工具说明、参数和调用入口。服务越来越多时，工具接入本身就成了一项重复工作。

MCP 提供了统一的工具发现和调用方式：server 提供有哪些工具、如何传参，以及执行入口；Agent 运行时负责把发现的工具交给模型，并在执行前检查权限。本节从 S04 的基础工具与 Hook 出发，单独演示这个接入过程。

**教程里的 `docs` 和 `deploy` 是进程内模拟服务。** 文档搜索、版本和部署状态都返回预设文本，没有连接真实文档平台或部署系统。这里先理解发现与分发的机制，真实 MCP 的通信连接不在本节实现。

以“搜索 agent hooks，并告诉我文档 API 版本”为例：

```text
第一次请求模型：基础工具 + connect_mcp
        ↓
模型调用 connect_mcp("docs")
        ↓
运行时保存服务返回的工具定义和调用入口
        ↓
下一次请求模型：基础工具 + connect_mcp + docs 的工具
        ↓
模型选择 search / get_version → 权限检查 → 服务执行
        ↓
结果加入对话 → 模型继续回答
```

`assemble_tool_pool()` 在每次请求模型前重新组装工具池。因此连接成功后，新工具从下一次模型请求开始可见。模型仍然通过工具名和参数提出行动，执行结果仍然进入已有的反馈循环；增加工具来源不需要另写一套 Agent Loop。

模型看到的外部工具名带有服务前缀，例如 `mcp__docs__search`。这样 docs 和其他服务都提供 `search` 时，运行时仍能区分它们。真正调用服务时，分发表会把这个名字映射回原始工具名 `search`。工具说明和参数结构来自发现结果，调用入口也同时加入分发表。

外部服务描述自己能做什么，并不代表它可以决定哪些操作已经获得授权。本节使用宿主配置的策略：

| 外部工具 | 宿主策略 |
|---|---|
| docs 搜索、查询版本 | 直接允许 |
| deploy 查询状态 | 直接允许 |
| deploy 触发部署 | 用户确认 |
| 没有配置策略的外部工具 | 用户确认 |

即使服务把某个工具标注为“只读”，运行时也不会据此自动放行。权限检查仍挂在工具执行前的 Hook 上。缺少必填参数或多传参数导致的调用异常，会作为错误结果交回模型，让它有机会修正请求。

可以运行后输入“连接 docs server，搜索 agent hooks，并告诉我当前文档 API 版本”，观察 `connect_mcp → mcp__docs__search / get_version` 的过程。再输入“连接 deploy server，查看 web 服务状态，不要触发部署”，比较查询状态与触发部署的权限差异。

与教程的差异限于 OpenAI 协议适配（包括工具格式、消息格式和结束原因检查），以及项目既有的 `.env` 加载与 CLI 初始化方式。内部的工具发现、命名、宿主策略、分发和基础工具函数保留教程实现。

**升级后的理解：工具集合可以在运行时扩展。外部服务负责提供能力，Agent 运行时负责发现、命名、授权和分发，模型继续在同一个行动反馈循环中选择并使用这些能力。**

## S15：从独立机制到一个能协同工作的运行时

代码：[s15_integrated_harness.py](s15_integrated_harness.py)

**前面实验的局限：** 各节分别说明了工具、权限、记忆、后台执行和团队，但它们没有始终运行在一起。例如 S11 可以后台运行命令，却没有 S09 的记忆；S14 可以发现外部工具，却没有 S13 的队友。要让它们共同完成任务，需要明确各自接入循环的位置，以及哪些状态可以共享。

S15 沿用教程，把这些机制放进一个独立实验，提供 26 个内置工具。它没有另发明一种 Agent 决策方式，主线仍然是模型提出行动、程序执行、结果交回模型。整合的重点变成了每次请求前如何准备信息、执行时如何控制，以及其他线程的事件何时回到对话。

```text
用户输入 / 定时到期 / 后台完成 / 队友事件
                       ↓
              等主 Agent 空闲，启动回合
                       ↓
       注入通知 → 压缩上下文 → 召回相关记忆
                       ↓
       组装系统提示词与当前工具池 → 请求模型
                       ├─ 没有工具调用 → 结束 Hook → 提取长期记忆
                       └─ 有工具调用 → 权限与前置 Hook
                                             ↓
                              普通执行 / 后台启动 / 委派
                                             ↓
                              执行结果或启动确认加入对话
                                             ↓
                                         下一次请求
```

例如用户要求“后台运行检查，同时阅读说明文档，最后汇总”。前台先确认 Shell 调用，程序启动后台命令，并把启动确认交回模型；模型可以继续读取文档。命令结束后，通知进入主对话，模型据此汇总。如果模型已经结束回合，事件线程会在 Agent 空闲时主动唤醒它，不必等用户再输入“检查结果”。这补上了 S11 中完成通知不能主动启动回合的限制。

### 每种状态有自己的位置

整合并不意味着把所有信息塞进一份共享历史：

| 状态 | 在整合运行时中的位置 |
|---|---|
| 当前用户要求、行动和结果 | Lead 的对话历史 |
| 当前计划 | 内存中的 Todo 清单 |
| 可恢复的工作进度与依赖 | `.tasks/` 中的任务图 |
| 跨会话仍有用的知识 | `.memory/` 中的记录，按相关性召回 |
| 技能操作指南 | 系统提示词先放目录，需要时调用 `load_skill` |
| 队友的调查细节 | 队友自己的上下文，通过收件箱回传结果 |
| 过长的原始输出和历史 | 外部文件留档，对话中保留预览、路径或摘要 |

任务图决定能否认领，Todo 帮助保持当前计划，记忆保存以后仍有用的知识；它们不能互相替代。任务或清单上的“完成”仍由模型更新，需要结合实际文件与验证结果判断。

### 事件可以异步到达，主对话仍按顺序推进

定时线程、后台命令和队友可以独立运行。主 Agent 的前台回合与自动回合共用一把锁，避免同时修改同一份历史。事件到达后可以排队，等待当前回合结束；工具调用与对应结果必须成对进入后续模型请求。

一次性子 Agent 和持久队友继续保存各自的历史。子 Agent 的最终摘要作为工具结果返回；持久队友通过消息事件与 Lead 协作。任务绑定的 worktree 继续决定队友工具的工作目录，成果的检查与整合仍需另外完成。

### 长任务需要管理上下文和恢复请求

每次调用模型前，程序依次尝试保存过大的工具输出、归档过长历史、缩短已经读取的旧结果，仍然超限时再请求摘要。压缩后的当前要求单独标为权威指令，摘要只是参考状态，不能替用户授权新操作。

模型调用还接入教程的恢复机制：遇到 429 或服务端 5xx 错误时退避重试；如果明确配置了 `FALLBACK_MODEL_ID`，连续服务错误可以切换该模型。输出被截断时先提高输出额度，再尝试继续；上下文过长时执行 reactive compact 后重试。OpenAI 的状态码参照[官方错误码文档](https://developers.openai.com/api/docs/guides/error-codes)。截断的工具参数不会进入执行，也不会作为未配对的调用进入下一次请求。

记忆召回、回合后的知识提取和必要的历史摘要都可能增加模型调用。它们服务于上下文准备与持久化，不代表用户又发起了新的任务。

### 本节的边界与适配

教程 S15 收紧了权限：**每条 Bash 命令都需要前台确认；自动回合和队友线程中的 Bash 会被拒绝。** 因此定时回合可以生成提醒、使用获准的文件工具，但不能无人确认地运行 Shell。外部文件访问直接拒绝，MCP 的非白名单工具也需要前台确认。

MCP 继续使用 S14 的进程内模拟服务，仍没有真实的 MCP 通信。技能素材使用 `experiments/skills/`，记忆模块复用本项目的 `s09_memory.py`。运行数据仍相对于启动时的工作目录保存。

实现尽量保留教程的内部工具块、压缩流程和协作逻辑，在 `request_model()` 边界转换 OpenAI 消息、工具声明与响应，并把服务错误恢复适配为 OpenAI 状态码。模型与 `.env` 初始化、退出时的 Shell 清理注册放在 CLI 入口。另一个必要差异是兼容已有 S12 定时记录的 `last_fired` 字段；读取损坏的定时文件会直接报错，避免原版忽略读取失败后覆盖已有记录。

可以先输入“连接 docs，查询文档版本；再读取 README.md 并概括项目目标”，观察动态工具与文件工具在同一轮协作。再尝试后台命令或仅本次会话有效的定时提醒，观察工具确认、异步通知和自动回合如何衔接。

**升级后的理解：Agent 内核除了推进模型与工具之间的反馈，还要组织上下文、权限、持久状态和事件。不同机制各自维护状态，通过明确的入口进入同一个运行时。**

## S16：从模型逐步决定行动到脚本编排固定流程

代码：[s16_workflow_runtime.py](s16_workflow_runtime.py)

**上一节的局限：** S15 已经能调工具、派子 Agent、接收队友消息，但每一步怎么安排，仍然需要模型在对话中决定。遇到不确定的任务，这种灵活性很有用；遇到反复执行的固定流程，每次都重新安排就不必要了。

例如代码审查可以固定为：分别检查正确性、安全、性能和风格，再逐条验证发现，最后按严重程度汇总。各步如何分析需要模型判断，但“先检查，再验证，最后汇总”的顺序可以直接写成 Python 函数。

S16 在 S15 的工具池里增加 `Workflow`。模型选择已注册的工作流并传入参数，运行时找到对应函数，执行整个流程，将结果作为一次工具结果交回主 Agent。

```text
用户：审查这段代码改动
          ↓
主 Agent：Workflow(name="review-changes", args={"changes": "代码内容"})
          ↓
已注册的 Python 工作流
    ├─ 正确性：检查 → 逐条验证 ─┐
    ├─ 安全：  检查 → 逐条验证 ─┤
    ├─ 性能：  检查 → 逐条验证 ─┤→ 汇总确认的问题
    └─ 风格：  检查 → 逐条验证 ─┘
          ↓
一次工具结果返回主 Agent → 生成回答
```

模型提交的是名称和数据。可执行函数由宿主保存在 `WORKFLOWS` 中，当前示例是 `review-changes`。增加另一种固定流程时，再编写函数并注册即可。

### 模型处理内容，代码控制步骤

工作流中的 `ctx.agent()` 是一次独立的模型请求，只收到该步的提示词和传入内容，没有文件或 Shell 工具，也不继承主 Agent 的完整历史。因此，审查文件前，主 Agent 需要先读取内容，再放入 `args.changes`；只传路径并不能让工作流读到文件。

| 原语 | 用途 | 在示例中的位置 |
|---|---|---|
| `agent()` | 请求模型完成一个局部步骤 | 检查一个维度，或验证一条发现 |
| `parallel()` | 同时开始一组调用，等全部结果回来 | 验证某个维度的所有发现，然后筛选 |
| `pipeline()` | 每个输入独立经过多个阶段 | 每个审查维度各自经过“检查 → 验证” |
| `phase()` / `log()` | 输出阶段与过程信息 | 标记 Review、Verify，报告汇总数量 |
| `workflow()` | 调用另一个已注册的流程 | 教程支持一层嵌套，共用预算和调用限制 |

`pipeline()` 不需要等所有维度检查完再开始验证：安全检查先完成，就可以先验证安全问题，此时性能检查可能还在运行。`parallel()` 则会等待当前这组验证全部返回，再把结果交给后续代码。

中间结果保存在工作流的变量里。模型输出 findings 后，程序需要按字段读取和筛选，因此每步可以提供 schema，要求返回 JSON。运行时解析并校验，不符合时重试一次，再失败就将工作流标记为失败。这里沿用教程的“提示词要求 JSON + 本地校验”，没有另接 OpenAI 的 Structured Outputs 接口。

### 恢复的是已完成的模型调用

假设四个维度中，正确性检查及验证已经完成，安全检查也完成了，但后续模型请求失败。如果从头重做，已经拿到的结果也要重新请求。

运行时为每次执行生成 `runId`，将快照、最终输出和逐步追加的 journal 保存在 `experiments/.runtime/`。每个成功完成的 `agent()` 都会把结果写入 journal，供恢复时读取。

再次调用时传入 `resume_from_run_id`，工作流函数会重新执行。到达 `agent()` 时，程序根据标签、提示词和 schema 等调用内容查找日志：有结果就复用，没有才请求模型。因此前面已经完成的检查可以跳过模型请求，失败或尚未开始的步骤继续运行。

这不是恢复整个 Python 进程，也不会撤销或跳过任意代码的副作用。它复用的是日志中的模型结果；编写工作流时仍需要理解函数会重新执行。缓存结果也不会因为换了模型而自动失效。

### 观察进度与执行边界

`phase("Verify")` 表示某条执行路径进入验证阶段，不意味着所有维度都完成了检查。和 S05 一样，进度文字需要结合实际执行结果理解。工作流的 `completed` 表示脚本正常返回，也不代表模型确认的问题一定正确。

本节沿用教程：`Workflow` 工具会等待整段流程结束后，返回启动信息、结果和任务状态。虽然事件名包含 `async_launched`，它并没有立即释放主 Agent 去执行其他工具；内部各步的并发由异步编排和工作线程实现。

交互模式使用与 S15 相同的 OpenAI client 和当前模型，各步骤的 token 用量来自 API 响应，供预算统计使用。预算是在请求返回后累计检查的，不能保证请求前精确限制费用。实现保留教程的调度、校验和恢复逻辑，主要调整 API 调用、S15 文件路径以及交互入口的 `.env` 初始化。

可以先离线观察流程和缓存，不需要 API Key：

```bash
uv run experiments/s16_workflow_runtime.py demo
uv run experiments/s16_workflow_runtime.py resume
```

第一次使用教程的确定性模拟结果展示流程；第二次会看到 `status=cached`，相同调用不再请求 runner，新增模型调用数和 token 数都是 0。

使用真实模型时运行：

```bash
uv run experiments/s16_workflow_runtime.py
```

例如输入：“读取 experiments/s02_tool_use.py，把代码内容传给 review-changes 工作流进行审查，最后汇总确认的问题。”这时主 Agent 负责读取和发起工作流，脚本负责固定的检查与验证顺序。

**升级后的理解：Agent 可以把重复的协作顺序交给已保存的代码。模型负责各步内容判断，运行时负责并行推进、结果校验和日志恢复，再把整体结果交回行动反馈循环。**

## S17：从结束一个回合到检查目标是否完成

代码：[s17_goal_loop.py](s17_goal_loop.py)

**前面循环的局限：** 模型没有再请求工具，程序就结束当前回合。但“模型想停下”与“用户要求已经完成”是两件事。例如用户要求修到测试通过，模型可能改完代码就回答“已修复”，却没有运行测试。

S16 可以把一套固定流程执行完，但流程正常结束，也不等于最终目标达成。S17 关注的是退出时的判断：保存一个可检查的完成条件，在主模型准备结束时，由一次独立模型调用检查对话中的证据。

```text
/goal check.py 输出 verified，且退出码为 0
                    ↓
           主模型使用工具推进任务
                    ↓
             主模型不再请求工具
                    ↓
       判断器读取完成条件和最近的对话
          ├─ 条件满足 → 标记 achieved，返回
          ├─ 条件未满足 → 把缺少的证据加入对话 → 主模型继续
          └─ 无法完成 → 标记 failed，返回
```

### 干活和判断分成两次调用

主模型可以读写文件、执行命令。判断器没有工具，只收到完成条件和整理后的对话记录，返回 `ok`、`reason` 和 `impossible` 三个字段。

例如主模型说“实现已经改好”，判断器发现没有测试输出，可以返回：

```json
{"ok": false, "reason": "还没有运行测试并提供退出码", "impossible": false}
```

程序把这个理由作为一条新消息加入原来的历史，再次请求主模型。主模型看到反馈后运行测试，工具将输出和 `exit_code` 写回对话；主模型再次准备停止时，判断器才能看到这些新证据。这个过程不需要用户反复输入“继续”。

两种调用默认使用同一个 `MODEL_ID`，但判断器有独立提示词，也不会获得主模型的工具。需要时可通过 `GOAL_EVALUATOR_MODEL_ID` 指定另一模型。“独立”指职责和请求分开，不要求使用不同型号的模型。

### 完成条件要写清楚，证据仍然要由工具取得

“把项目弄好”很难判断；“生成 result.txt，文件内容是 hello，并读取文件确认”则有明确的结束状态和验证方式。输入 `/goal <条件>` 会同时保存目标并开始执行，无需再发一条“开始”。

这也回应了 S05 的进度问题：Todo 中勾选完成不能证明工作已经完成。Goal 判断器会再检查对话中的内容，但它仍然是模型，可能误判；它不会自己打开文件或重跑命令，不能替代测试和实际产物检查。把真实命令结果写入对话，是让它有据可查的前提。

### 自动继续需要明确的出口

| 情况 | 返回状态与后续行为 |
|---|---|
| 没有设置目标 | `allow`，按普通 Agent 回合结束 |
| 判断条件满足 | `achieved`，清除活跃目标并保留完成记录 |
| 判断无法完成 | `failed`，清除活跃目标并保留失败原因 |
| 判断器调用失败或输出不合法 | `error`，停止自动继续，保留目标 |
| 连续未完成达到限制 | `limit`，返回控制权，保留目标 |
| 主循环达到 `max_turns` | `max_turns`，返回控制权，保留目标 |
| 宿主报告后台工作仍在运行 | `defer`，暂不调用判断器，保留目标 |

教程默认允许 Stop 检查连续要求继续 8 次，下一次仍未满足时返回 `limit`。用户补充信息后可以继续，也可以清除目标。`MAX_TURNS` 则控制一次请求内的主模型调用次数，包含使用工具的轮次，默认不设置这项上限。两种限制都不会把尚未完成的目标标记为成功。

后台任务的结果尚未到达时，判断通常为时过早。代码提供 `background_running` 和 `submit_background_result()` 两个宿主接入点：先暂缓判断，收到结果后再进入同一循环。本节本身没有启动后台任务的工具，也没有接入 S16 的 Workflow。

### 使用方式与本节范围

沿用教程，S17 是基于 S04 的独立机制实验，保留 Bash、读文件、写文件、编辑文件和查找文件五个工具，以及执行前后的 Hooks。它没有继承 S15 的所有机制。权限也沿用本节原版：普通 Shell 命令可以直接执行，命中禁止项则拒绝，匹配破坏性操作规则时询问用户；这些规则仍是教学示例。

运行交互模式：

```bash
uv run experiments/s17_goal_loop.py
```

例如输入 `/goal 创建 result.txt，内容为 hello，并读取文件确认`。之后可用以下命令管理当前目标：

- `/goal`：查看条件、判断次数和最近原因；token 统计只包括主模型调用，判断器另有 API 用量。
- `/goal 新条件`：替换当前目标，并立即执行新任务。
- `/goal clear`：清除目标。

也可以从命令行直接发起任务，并限制主模型调用次数：

```bash
MAX_TURNS=10 uv run experiments/s17_goal_loop.py "/goal 创建 result.txt，内容为 hello，并读取文件确认"
```

Goal 状态和事件保存在当前会话内存中。`restore()` 能从宿主提供的事件恢复仍活跃的条件，但本节 CLI 不保存和恢复整个会话；退出后不会自动续跑。它与 S16 从磁盘 journal 复用步骤结果的机制各自解决不同问题。

实现保留教程的 GoalController 和继续执行流程，在 API 边界转换 OpenAI 消息与响应，加载项目根目录的 `.env`。模型响应被截断时明确报错，避免把未完成的输出当成完成判断，或执行残缺的工具参数。

**升级后的理解：模型提出结束当前回合，只是一个停止请求。运行时还可以根据用户明确的完成条件检查证据，将未完成的工作送回同一个行动反馈循环。**
